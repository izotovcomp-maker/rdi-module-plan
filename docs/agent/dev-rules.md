# Правила разработки

Вынесено из AGENTS.md. Читай, когда пишешь или меняешь код: API-эндпоинт, фича,
плейсмент, cron, доступ, REST-вызовы.

## Как агент работает в этом проекте

- **Install-flow** уже зашит — двухфазно через `state` + `installFinish` + reload. См. [rule-b24-install-checklist](/projects/docs/rules-b24/rule-b24-install-checklist.md)
- **Доступ к приложению** — из коробки три режима с переключателем в окне «Доступ» (действует один, права режимов не пересекаются; администраторы портала допущены всегда): **по отделам** (по умолчанию), **персонально** (список всех учётных записей: Фамилия Имя, почта, id), **всем на портале**. Режим и списки администратор выбирает сам кнопкой «Доступ» — в онбординге это не спрашиваем. Начальный режим — `DEFAULT_ACCESS_MODE` в `www/api/session.php`, отдел по умолчанию — `DEFAULT_ALLOWED_DEPARTMENTS`; право `department` нужно режиму по отделам (он по умолчанию), остальным режимам хватает `user`. Нужна своя механика — доработка `accessAllows()`. См. [rule-b24-department-based-access](/projects/docs/rules-b24/rule-b24-department-based-access.md)
- **REST-вызовы** — через `$b24 = b24(); $b24->call('method', [...])`. Для CRM сущностей предпочитать `crm.item.*` с `entityTypeId`, не legacy `crm.<entity>.*`. См. [rule-crm-item-universal-api](/projects/docs/rules-b24/rule-crm-item-universal-api.md)
- **Имена пользовательских полей — только оригинальные, `UPPER_CASE`: `UF_CRM_8_O_CODE`.** Не `ufCrm8OCode`, не `ufCrm_8_O_CODE`, не `uf_crm_8_o_code`. Причина: `crm.item.*` по умолчанию (`useOriginalUfNames = N`) принимает и отдаёт `UF_*` в camelCase — модель копирует их из ответов, а потом имена приходится переделывать. Поэтому в **каждом** вызове `crm.item.*` (`add`, `update`, `get`, `list`, `fields`; `delete` параметр не принимает) `'useOriginalUfNames'` должен быть `'Y'`. `$b24->call()` и `batch()` подставляют его сами (`B24::withOriginalUfNames`), но не затирай явное значение и не ставь `'N'` — тогда и `fields`, и `select`, и `filter`, и `order`, и ответ используют `UF_CRM_…`. Код ответа читай по тем же ключам (`$item['UF_CRM_8_O_CODE']`). Стандартные поля `crm.item.*` (`title`, `stageId`, `assignedById`) остаются camelCase — правило только про `UF_*`. Остальные методы (`crm.status.*`, `crm.userfield.*`, `user.*`, `tasks.*`, `lists.*`) и так используют `UF_*` в оригинале. Имена полей смарт-процесса не угадывай и не собирай по шаблону: возьми из `crm.item.fields` (с `useOriginalUfNames = Y`) или из ответа человека через `debug.php`. См. [rule-b24-uf-names-uppercase](/projects/docs/rules-b24/rule-b24-uf-names-uppercase.md).
- **REST-вызов для N id (foreach)** — НЕ `foreach ($ids as $id) { $b24->call(...) }`, а `$b24->batch([...])` чанками по 50. См. [rule-b24-rest-batch-not-loop](/projects/docs/rules-b24/rule-b24-rest-batch-not-loop.md) — на практике разница 24-34с → 2-3с
- **State** — через `storeRead(FILE)` / `storeWrite(FILE, $data)`. Все state-файлы в `data/`, защищены `<?php exit;?>` префиксом
- **Безопасность** — «пользователь авторизован на портале Б24» защищает только вход, не то, что ему можно внутри приложения (все REST-вызовы идут одним общим admin-токеном, не токеном текущего юзера). См. раздел «Безопасность» ниже — читать **до**, не после написания кода.
- **Права приложения («Настройка прав»)** — см. [deploy.md](deploy.md), раздел «Права приложения». Появилась фича с новым правом — назови, какое право добавить, и что токен надо обновить.
- **Грабли и вопросы по Б24** — по цепочке из [b24-search.md](b24-search.md).

## Дебаг-кнопка — как получить данные портала

Агент сам не ходит на портал (сессия администратора, iframe, токены на сервере не читаем), поэтому данные
для разработки — названия и типы полей, пример записи, воронки и стадии, ответ метода — приходят через
кнопку **«Дебаг»**, которую видят только администраторы портала.

1. **Агент** пишет запрос в [`www/api/probe-task.php`](../../www/api/probe-task.php): `return function (callable $call) { return $call('crm.item.fields', ['entityTypeId' => 1268]); };`
2. Деплой (`bash deploy.sh`; на `prod` и `customer` — только по явной команде человека).
3. **Админ** открывает приложение из портала, нажимает «Дебаг» → в окне появляется текст (JSON) → «Копировать» → вставляет в чат.
4. Агент читает ответ и продолжает. Нужны другие данные — правит `probe-task.php`, снова деплой.

Правила:
- `probe-task.php` — **только чтение**: `get / list / fields / info / current / search / count` (в `batch` — каждая команда). Остальное блокирует `probe.php`.
- Обвязку `probe.php`, кнопку и окно не правь: правится только `probe-task.php`.
- Ограничивай вывод (`select`, `limit`): человек копирует его в чат. Токены и секреты из вывода вырезаются, но личные данные клиента — нет: не вытягивай лишнего.
- Имена полей — `UF_*` в `UPPER_CASE`, `crm.item.*` получает `useOriginalUfNames = Y` сам (см. выше).
- Отладка закончена — верни `probe-task.php` к заглушке. Эндпоинт доступен только админам, но не оставляй в нём запросы, которые не нужны.
- Ручной тестер `www/api/debug.php` остаётся для человека (произвольный метод в браузере); агент им не пользуется.

## Параметры, которые не вошли в онбординг

Собираются **лениво по факту запроса**:
- Юзер просит фичу со `lists.*` / задачами / телефонией → добавляю нужный scope в карточку local-app
- Юзер просит вкладку в карточке сделки / виджет → раскомментирую плейсмент в `www/api/bind.php` + добавляю scope
- Юзер просит фоновую обработку → активирую `www/bin/process.php` через панель cron
- Юзер говорит «cron не нужен» → удаляю `www/bin/process.php`

## Безопасность

**OAuth Б24 закрывает форму входа и подбор пароля — и только их.** Дальше
запрос долетает до вашего PHP на VPS, и там всё как в любом другом проекте:
секреты, доступ по ролям/отделам, IDOR, XSS, гонки состояний на файловом
сторе — целиком на коде этого проекта. Полный разбор, что именно снимает
архитектура, а что нет, по каждому классу риска — [/projects/docs/rules-b24/rule-b24-security-baseline](/projects/docs/rules-b24/rule-b24-security-baseline.md).

Когда читать файл — см. таблицу «Когда что читать» в [../../AGENTS.md](../../AGENTS.md).
Он прямо указывает, какие пункты касаются какого класса функциональности; перед
деплоем в прод — быстрый проход по актуальным пунктам, не формальность для галочки.
