# Журнал решений

> Здесь — **почему** проект устроен так, а не иначе. Каждое значимое
> решение: что выбрали, какие были варианты, почему именно это.
> Файл **только дописывается** (новые записи — вниз). Старые записи не
> удаляем: если решение отменили — добавляем новую запись «отменяет D-NNN».
>
> Зачем: чтобы следующий исполнитель не «переоткрывал» уже закрытые вопросы
> и не ломал то, что сделано осознанно. Один абзац здесь экономит часы.

Записывай решение, когда выбор был **неочевидным** или у него есть
последствия: скоупы, структура данных, плейсменты, обход бага и т.п.

## D-001 · Шаблон _b24-single-php (single-tenant PHP)
**Дата:** — · **Статус:** принято

**Контекст.** Стартовали новый проект для Битрикс24.
**Решение.** PHP-бэкенд, файловый store (`<?php exit;?>`-защита), vanilla JS, Netangels.
**Почему.** Готовый скелет с OAuth, install-flow, session-gate «из коробки».
Без БД, без composer — минимум зависимостей для single-tenant.
**Последствия.** Multi-tenant / маркет — смена шаблона, не доработка этого.

## D-002 · Переезд хостинга на VPS + Caddy + PHP-FPM
**Дата:** 2026-07-03 · **Статус:** отменяет хостинг-часть D-001

**Контекст.** D-001 фиксировал хостинг как Netangels (shared, `.htaccess`).
Команда перешла на собственный VPS с Caddy + PHP-FPM для всех B24-приложений.

**Варианты.** Остаться на shared-хостинге (Netangels) vs собственный VPS с
явной настройкой каждого проекта через Caddyfile.

**Решение.** VPS, домен `b24.blackboxbegin.space`, один Caddy-блок `handle
/<slug>*` на проект, деплой — локальный rsync (`bash deploy.sh`) прямо на
сервере, без SSH.

**Почему.** Больше контроля над PHP-FPM/Caddy-конфигом, не завязаны на
ограничения конкретного shared-хостера. Caddy не читает `.htaccess` —
защита state осталась той же (`<?php exit;?>`-префикс), это не пришлось
менять.

**Последствия.** `.htaccess`-независимость шаблона (D-001) оказалась кстати:
переезд не потребовал менять модель защиты. Появились новые следствия
Caddy `uri strip_prefix` — APP_URL нужно править вручную после `init.php`,
handler URL обязательно с `/index.php`, `template.html` вместо `index.html`.
Все зафиксированы в `CLAUDE.md` → «Caddy + PHP-FPM — следствия для шаблона».
Домен, а не IP — при смене хостера под тем же доменом менять ничего не
нужно; деплой на сервер заказчика с другим доменом — отдельный кейс,
не покрыт этим решением.

## D-003 · env.php генерируется deploy.sh, init.php — только для 1%-кейса
**Дата:** 2026-07-04 · **Статус:** принято, уточняет D-002

**Контекст.** После D-002 конвент деплоя зафиксирован: домен всегда
`b24.blackboxbegin.space`, путь всегда `/var/www/b24/<slug>`. При этом
`APP_URL`/`APP_PATH`/`DATA_ROOT` стали полностью детерминированы из
одного значения (slug), но флоу продолжал требовать открыть `init.php`
в браузере и вручную поправить `APP_URL` (следствие `uri strip_prefix`
из D-002). На практике оба реальных проекта на VPS (`ap-simple-test`,
`fv-taskindep-panel`) этот шаг обошли — `env.php` был написан вручную
напрямую, `init.php` на сервере не оказывалось вообще (`deploy.sh` его
и не копирует, см. `--exclude 'init.php'`), задокументированный флоу
не воспроизводим на свежем сервере как описано.

**Варианты.** (а) Почистить `deploy.sh`, чтобы `init.php` таки доезжал
до сервера при первом деплое — оставить flow как есть. (б) Убрать
`init.php` из основного flow, генерировать `env.php` детерминированно
прямо в `deploy.sh`, оставить `init.php` в шаблоне только как fallback
для хостинга, где путь/домен заранее не известны (shared-хостинг
заказчика, FTP).

**Решение.** (б). `deploy.sh` при первом деплое slug'а (env.php на
сервере ещё нет) генерирует `env.php` из `env.example` подстановкой
`APP_URL=https://b24.blackboxbegin.space/<slug>`, `APP_PATH=DEPLOY_DIR`,
`DATA_ROOT=DEPLOY_DIR/data`. Человеку остаётся вписать только
`B24_CLIENT_ID`/`SECRET` — их и так нельзя получить иначе, кроме как
из карточки local-app в Б24. `init.php` физически остаётся в шаблоне
(`www/init.php`) как есть, без изменений — для кейса, где конвент
VPS+Caddy не применим (хостинг заказчика с непредсказуемым путём).

**Почему.** Автоопределение `APP_URL` через `init.php` было нужно для
общего случая (произвольный shared-хостинг, куда шаблон изначально
целился) — на своём VPS с фиксированным конвентом это лишний шаг,
который к тому же не работал как описано (см. «Контекст»). Убирать
`init.php` из репозитория целиком не стали — шаблон должен оставаться
пригодным не только для нашего VPS.

**Последствия.** `how-to-link.md` описывает только 99%-кейс (наш VPS,
`deploy.sh`). Новый файл `how-to-link-ALL.md` — процедура для 1%-кейса
через `init.php`, на него ссылаются `how-to-link.md`, `README.md`,
`CLAUDE.md`. `docs/state.md`-чеклист (шаблонный, наследуется новыми
проектами) обновлён под новый flow.

## D-004 · Статусы и 6 диапазонов стадий — из портала, не считает приложение
**Дата:** 2026-10-11 · **Статус:** принято

**Контекст.** Цвета плашек статусов брались из воронки смарта 1050 (категория 20):
`crm.status.list ENTITY_ID=C1050:20` дал реальные цвета; карту `STATUS_ID → сокращение
(≤4 символа) / цвет` зафиксировали (NEW→Зап #000000, PREPARATION→Расм #88b9ff,
CLIENT→Разр #10e5fc, UC_AJTX21→Корр #ace9fb, UC_PM02XS→Ожид #fff300,
UC_M71TWU→Согл #00a74c, SUCCESS→Завр #00ff00, FAIL→Анну #ff0000). Даты 6 стадий —
не вычисляет приложение: Запуск = dstart этапа (UF_CRM_10_MST_DSTART) →
UF_CRM_14_MOD_RUN; Рассмотрение = MOD_RUN → MOD_CHECK; Разработка = MOD_CHECK →
MOD_CREATE (акцент); Корректировка = MOD_CREATE → MOD_EDIT (длительности UF_DAY2_*);
Ожидание → MOD_WAIT; Согласование → MOD_APPROVE. При правке длительностей на клиенте
даты дочерних стадий пересчитываются живьём (портал напишет те же значения через БП).

**Следствие.** api/graph.php отдаёт dstart/runD/editD/waitD/approveD и status/statusColor;
локальный пересчёт только как предпросмотр до сохранения.

## D-005 · Привязка плейсмента — кнопкой «Плейсменты», dealId из PLACEMENT_OPTIONS
**Дата:** 2026-10-11 · **Статус:** принято, в шаблоне остался долг

**Контекст.** Двухфазный install шаблона не делает placement.bind автоматически
(комментарий в bind.php — план). Привязку сделали админ-кнопкой «Плейсменты» в тулбаре
(bind.php?format=json, вызов из фрейма с сессией). DealId приходит обработчику в POST
`PLACEMENT_OPTIONS` (JSON с ключом ID) — index.php парсит и прокидывает
`window.APP_DEAL_ID`; query-параметры — фолбэк.

**Следствие.** При смене кода плейсмента/названия — нажать «Плейсменты» заново
(идемпотентно: unbind+bind). Долг шаблона: авто-бинд в фазе 2 install-flow.

## D-006 · crm.item.list только noselect: select на этом портале молча режет ответ

**Контекст.** График на реальных данных приходил пустым. Дебаг-матрица (4 прогона
probe) показала кворк портала ooordi (Б24 облако, осень 2026) в `crm.item.list`:

- `useOriginalUfNames=Y` + `select` → в items **только UF-поля**, системные
  (id, title, stageId, parentId1042) молча выкинуты;
- `useOriginalUfNames=N` + `select` с UPPER_CASE UF → UF **молча выкинуты**
  (системные возвращаются); тот же вызов с `useOriginalUfNames=N` без select — полный;
- `Y` без select → всё на месте: системные ключи camelCase, UF — UPPER_CASE;
- `crm.item.fields` на этом портале возвращает пусто (без ошибки) — имена полей
  снимали из noselect-items;
- `limit`/`order` параметрами crm.item.list не являются (limit игнорируется);
  фильтр привязки — `parentId1038`/`parentId1042` (camelCase, не PARENT_ID_1038).

**Решение.** В `graph.php` `crm.item.list` вызывается **без select** (b24() сама
ставит `useOriginalUfNames=Y` по правилу UPPER_CASE UF). Полнотекстовые ACT-поля
(истории) в 1042/1050 умеренные — объём ответа приемлем. num/sname берём из
`UF_CRM_14_MOD_NUM/SNAME` (fallback — regex по title), привязка к этапу — ключ
`parentId1042`.

**Следствие.** Если на других порталах кворк не воспроизводится — не страшно:
noselect работает везде. Если объём ответа станет проблемой (сотни модулей с
большими текстами) — пересмотреть на два запроса (Y+noselect минимально / N+select
системных) с merge по id.

## D-007 · Пагинация crm.item.list: total и next — на верхнем уровне ответа

**Дата:** 2026-10-12 · **Контекст:** график терял 15 из 65 модулей (всю вторую
страницу: ids 292–320), `truncated: false`, ошибок нет.

**Диагноз (2 Дебаг-прогона):** портал отвечает честно (page1 total=65/next=50/n=50,
page2 n=15, batch k1_items=15, result_error пуст), а `graphListAll` читал `next`
из `$response['result']['next']`. У `crm.item.list` **`next` и `total` лежат рядом
с `result`** (верхний уровень ответа), внутри `result` — только `items`. Чтение
изнутри давало всегда `null` → ветка пагинации не запускалась молча.

**Почему пропустил локальный тест:** заглушка `FakeB24` в test-b1 клала `next`
внутрь `result` — под ожидание кода, а не под реальный портал. Классическая ловушка
TDD: заглушка копирует багу. Заглушка переписана на реальную форму (проверено
сырыми Дебаг-данными), тест RED → фикс → GREEN.

**Решение.** `graph.php`: `$next = $response['next'] ?? null` (верхний уровень).
В batch-ответах для каждой команды `next` живёт в общем `result_next` (ключи = ключи
команд) — graphListAll его не использует: все старты страниц считаются заранее из
`total`, cap — GRAPH_MAX_PAGES.

## D-008 · Интервалы Ганта считаются на клиенте от check/create; в Б24 — только 7 полей; пустые Д = 0 с авто-правкой

**Дата:** 2026-10-12 · **Контекст:** ТЗ пользователя на ДР-колонку
(UF_CRM_14_MOD_DAY2_CHECK) и новые интервалы стадий.

**Решение (по явному ТЗ и уточнениям пользователя):**
1. Полосы Ганта строятся ТОЛЬКО от якорей check/create + 5 длительностей;
   dstart этапа и хранимые даты runD/editD/waitD/approveD в полосах не участвуют
   (раньше Запуск считался от dstart).
2. Пересчитанные даты стадий на портал НЕ пишутся — их пересчитывает БП портала.
   Save-whitelist = ровно 7 полей: 2 даты (CHECK/CREATE) + 5 длительностей
   (DAY2_RUN/CHECK/EDIT/WAIT/APPROVE).
3. Пустая длительность при загрузке показывается как 0 и сразу кладётся в правки
   (pending) — отправка нормализует нули в Б24 у всех модулей, включая
   незапланированные (без дат). Ошибка валидации «Длительность не задана» удалена.
4. Нулевая/пустая длительность → полоса стадии не рисуется; нет check или create →
   полос нет вовсе.
5. Цвета полос — палитра плашек стадий из crm.status.list (та же, что у бейджей);
   stageColors отдаёт сервер (суффикс STATUS_ID → COLOR).

**Почему так:** пользователь явно зафиксировал пункты 2–3 («результаты пересчётов
на портал не возвращаем», «пиши 0 и сразу считай исправлением для отправки»).
Чистая логика вынесена в www/js/gantt-logic.js (+node-тест) — тестируемость и
переиспользование в макете.
