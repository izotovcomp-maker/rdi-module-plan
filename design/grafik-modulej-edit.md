# Дизайн: режимы редактирования графика модулей

> Проект «График модулей» (rdi-module-plan). Дизайн согласован человеком в чате 2026-10-11.
> Основа: ТЗ `source/1st brief.md`, концепция стадий из `source/RDI Модули.md`.

## Проблема

График модулей (таблица этапов→модулей + Гант) в первой версии только просматривался.
Нужен удобный просмотр **и редактирование** сроков и длительностей: единичное и
групповое, с накоплением правок и отправкой одним batch-запросом, без REST на каждое
изменение.

## Цели

1. Два режима правки: **единичный** (инлайн-правка всех 6 полей) и **групповой**
   (чекбоксы модулей + закреплённое окно ввода над графиком).
2. Правки копятся локально, отправляются **одним batch** по кнопке «Отправить изменения»
   с подтверждением («Отправить N изменений в Б24?»). Счётчик N = число модулей с правками.
3. Кнопка «Отменить изменения» — полный перезапрос данных с портала.
4. Sticky: панель инструментов, заголовки таблицы + шапка календаря Ганта при вертикальном
   скролле; колонка названий при горизонтальном.
5. Гант перерисовывается **сразу** при каждом изменении (проекция исходное+pending),
   без ожидания отправки.

## Не-цели

- Пересчёт вычисляемых дат стадий (Запуск, Корректировка, Ожидание, Согласование,
  Длительность разработки) — делает БП портала.
- Создание/удаление модулей и этапов, смена стадий, оплаты, цены, «Процент модуля».
- Кэш данных, черновики на сервере, история правок, одновременная работа нескольких
  пользователей (последняя отправка перезаписывает).

## Режимы

- Тумблер на панели инструментов: `Единично | Группово`. Строго один режим.
- **Единичный:** чекбоксов нет; все 6 полей редактируются инлайн в ячейках таблицы
  (Рассмотрение, Разработка, З, К, О, С).
- **Групповой:** колонка чекбоксов слева (у этапа — чекбокс «выбрать все модули этапа»);
  над таблицей закреплено окно группового ввода с 6 полями и кнопкой
  «Применить к отмеченным (N)» (активна при N≥1 отмеченных). **Все 6 полей, пустые
  пропускаются** — применяются только заполненные, всем отмеченным модулям.
- В групповом режиме инлайн-правка недоступна.

## Накопление правок

- Локальная карта `pending: {moduleId: {поле: значение}}`.
- Правка сравнивается с исходным значением: возврат к исходному удаляет правку из карты.
- Изменённые ячейки подсвечены жёлтым. N = число модулей в карте.
- Гант: каждое изменение сразу пересчитывает полосы затронутых модулей (акцентная полоса
  Рассмотрение→Разработка, вторичные — остальные стадии). Валидация — только при отправке.
- Таблица не перестраивается при правках.

## Отправка и отмена

1. Валидация: у каждого модуля с правками Рассмотрение ≤ Разработка, длительности ≥ 0.
   Ошибки: модуль красным + список ошибок, отправка заблокирована.
2. Диалог подтверждения «Отправить N изменений в Б24?» (Да/Отмена).
3. Успех: batch `crm.item.update` чанками по 50 → перезагрузка данных с портала
   (БП пересчитает остальные стадии), сброс карты, тост «Сохранено: N модулей».
4. Ошибка REST: тост с текстом, правки остаются в карте.
- «Отменить изменения» при N>0: подтверждение «Сбросить N изменений?» → полный
  перезапрос и перерисовка.

## Sticky и прокрутка

- Единая вертикальная прокрутка таблицы и Ганта (строки всегда выровнены с полосами).
- Sticky строки: панель инструментов; заголовки таблицы + двухуровневая шапка календаря.
- Sticky колонка названий (и чекбоксов) при горизонтальном скролле.
- CSS `position: sticky`, без независимых скроллов.

## Масштаб Ганта

- Масштаб = **шаг дат в колонках**: 1 день (`15·16·17·18…`), 1 неделя (`1·8·15·22…`),
  2, 3, 4 недели.
- **Ширина колонки дат фиксированная** (px); меняется число дней в колонке:
  работа 01.01–07.01 при шаге «1 день» = 7 закрашенных колонок, при шаге «неделя» = 1.
- **Минимум 1 ячейка:** если длительность меньше шага (или даты равны), работа рисуется
  минимальной заливкой в одну ячейку — с Ганта не пропадает.
- «Смещение» (первая дата календаря) по умолчанию = самая ранняя дата модулей минус один
  шаг масштаба. Смена масштаба/смещения не требует перезагрузки данных.

## Данные и API

- **Загрузка** `api/graph.php?dealId=<ID>`: наш PHP-сервер собирает модули
  (`crm.item.list`, entityTypeId=1050, filter `PARENT_ID_1038`) и этапы (1042) через
  `$b24->batch()` чанками по 50; если модулей >50 — сервер в цикле запрашивает следующие
  страницы (параметр `start`), Б24 ничего сам не собирает. Ответ одним JSON:
  `{ stages[], modules[], serverTime }`, даты `YYYY-MM-DD`, длительности числа.
- **Сохранение** POST `action=save`: `{ updates: [{id, fields:{...}}] }`; сервер
  валидирует (id принадлежит сделке, только разрешённые поля) и отправляет batch
  `crm.item.update` чанками по 50. Ответ `{ saved, errors }`; без ошибок клиент
  перезагружает данные.
- **Разрешённые поля записи:** `UF_CRM_14_MOD_CHECK`, `UF_CRM_14_MOD_CREATE`,
  `UF_CRM_14_MOD_DAY2_RUN`, `UF_CRM_14_MOD_DAY2_EDIT`, `UF_CRM_14_MOD_DAY2_WAIT`,
  `UF_CRM_14_MOD_DAY2_APPROVE`.
- Доступ — стандартный `accessAllows()` (по отделам). Состояние правок только на клиенте.

## Граничные случаи

- Сделка без модулей: пустая таблица + плашка «Модули не заведены».
- Модуль без дат: поля пустые, на Ганте не рисуется; появляется при правке.
- Ошибка сети/сессии при загрузке: тост с ошибкой + кнопка «Повторить».

## Отклонённые альтернативы

- **Сохранение при каждом изменении** — отвергнуто: REST на каждое поле, перестройка.
- **Черновик правок на сервере** (`data/`) — YAGNI, правки живут только на клиенте.
- **Два независимых скролла таблицы и Ганта** — рассинхрон строк; выбран единый контейнер.

## Проверка

- Макет (`mock/`, выдуманные данные): тумблер режимов, чекбоксы, окно группового ввода,
  счётчик, диалоги подтверждения, sticky при скролле, все масштабы, минимум 1 ячейка,
  пустая сделка, модуль без дат.
- После деплоя: загрузка реальной сделки, единичная правка, групповая правка, отправка
  с подтверждением, отмена, валидация блокирует отправку при Рассмотрение > Разработка.
